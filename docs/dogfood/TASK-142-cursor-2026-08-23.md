# TASK-142 — Milestone F dogfood, Cursor

**Verdict: FAIL** · **Date:** 2026-08-23 · **Platform:** Windows 11 Home 10.0.26200

Repeats the TASK-141 clean-newcomer focus-timer path with Cursor, the third engine, so Milestone F
has evidence from all three. **The team built the feature correctly and it is green. The product
could not finish verifying it** — three attempts, no verdict, defeated by a process Isotopy itself
leaked and a timeout that discards everything it interrupts.

The headline in one line: **scope, design and implementation took 4 minutes 18 seconds and produced
a working, tested feature; verification then burned 1 hour 58 minutes across three attempts and
never returned an answer.** The Orchestrator recovered precisely twice and then stopped itself and
asked a sensible question rather than spinning. F's bar — *see the thing that was built* — was met
only after a human killed an orphaned process by hand.

**What killed it, in order:**

1. The **Developer** stage started `vite preview` on port 5180 and left it running.
2. The verify stage's 600s engine timeout fired and killed the `cursor-agent` process tree — **but

   hours later, its parent `cmd.exe` shim alive alongside it.
3. Isotopy's own product runner then tried to start the product and collided **with its own
   orphan**: `state: "exited"`, `lastError: "Process exited with code 1 — Port 5180 is already in
   use"` — while the app was serving happily at the configured URL the whole time.
4. QA spent its budget diagnosing that conflict ("Port 5180 is already in use — checking whether the

   and ran out of clock.
5. **Each retry started completely cold.** Cursor's `session_id` is parsed and discarded, so
   attempts 2 and 3 could not resume the QA agent's context and redid the Playwright setup from
   zero — into the same wall, twice.

## 13. Defects found, filed, not fixed here

1. **P0 — a stage's process tree survives the timeout that killed it.** `killProcessTree` uses
   `taskkill /pid <pid> /T /F`, but a `vite preview` started by the agent outlived it by two hours
   and held the port.
2. **P0 — Isotopy's product runner collides with its own orphan and reports the opposite of the
   truth.** `state: "exited"` with "Port 5180 is already in use" while the configured `healthUrl`
   returns 200. It should recognise a healthy product at its own URL rather than failing to start a
   second copy.
3. **P0 — the verify timeout discards everything it interrupts.** 600s elapsed, no verdict, no
   partial capture, and the stage is retried from nothing. Three attempts produced three total
   losses. Either the stage records progress, or the retry carries it.
4. **P1 — a stage reported "Timed out after 600s" after running 5316s.** The message and the
   measured duration disagree by 79 minutes. The stage did not settle when the timeout fired,
   almost certainly because the orphaned grandchild held the pipe open.
5. **P1 — Cursor's dropped session made every retry start cold**, which is the first *measured*
   cost of `TASK-154`'s first defect rather than an argued one. With session resume, attempt 2
   would have continued the QA agent's work instead of reinstalling Chromium.
6. **P1 — the CLI reports token usage and Isotopy throws it away.** Cursor's `result` event carries
   `usage` with `inputTokens`, `outputTokens` and cache counts; `resultSchema` in
   `cursor-protocol.ts` is `.passthrough()` and reads only `duration_ms`. "Cursor reports no
   tokens" was wrong — Isotopy discards them. No cost figure is emitted, so spend still needs the
   dashboard.
7. ~~**P2 — the composer displays the tier for a run that is pinned to a model.**~~ **Withdrawn** —
   see §4. The composer already says so and is tested; the finding was a misreading.
8. **P2 — onboarding**: the "Add project" control is absent from the panel that asks for it, and
   the folder picker has no path field (§4).

None fixed here. Milestone F admits nothing else; these belong to H or I.

## 16. macOS audit — reasoned through, not executed

No Mac was used. On macOS the Cursor adapter takes materially different branches:

- **Binary lookup** uses `which` with no `.cmd`/`.exe` extensions, so `commandNeedsWindowsShell` is
  false and the prompt goes via **argv**, not stdin — the opposite of the path exercised here, and
  the one guarded by `PROMPT_ARG_WARN_LENGTH`.
- **`install()` refuses outright** off win32 and returns a manual-install message.
- **Process cleanup** signals a process group with `SIGTERM` then `SIGKILL` instead of `taskkill /T`.
  Defect 1 above is a *Windows* observation; whether a POSIX process group would have taken the
  `vite preview` grandchild with it is unknown and worth checking, because if it would, defect 1 is
  Windows-specific and its fix is too.
